# 0.3.0
Analyze reworked. From a real run (a tight jump recorded at 14-29 FPS): "Macro repaired" 190 -> 192 (on a second recording 187 -> 190), then every window `none` and grey `?` rings. **Not run in Geometry Dash**; the logic is tested against the fake game (`tests/verify_sim_test.cpp` T22-T26).
- **Every window was `none` because of the RECORDING's flags, not because of the measurement.** A recording made at a low frame rate carries COARSE_INPUT and UNRELIABLE_TICK, and every click near such a flag was marked `UNRELIABLE` (never counted, grey `?` ring), while the popup before the analysis said the windows were still measured correctly. The windows are measured by replaying the level, and the check/fit has already proved that the macro passes, so these flags no longer exclude a click. Setting "Count clicks of a recording with a flagged tick counter" (on); off = the old rule.
- **Fit instead of repair.** At 14-29 FPS a frame is 8-17 ticks and the recorder stores the tick at the start of the frame, so a recorded click can be that far from the tick the game used (that is the 190 -> 192). A click that does not pass is moved by the smallest shift (+1, -1, +2, -2 ...; before: ten later shifts, then the earlier ones), the search covers at least one recorded frame each way, up to 400 trouble spots are fitted (before: 5, then every fix was dropped), the result lists each moved click as `recorded -> now` and shows the recorded ticks beside every row. The "Macro repaired" dialog and the COARSE_INPUT question before Analyze are gone (a short notification instead).
- **A saved state that does not restore exactly no longer makes a click UNRELIABLE.** `GameSimulator` trusts a saved state only after its offset-0 run reproduced the verified run; otherwise it replays from tick 0 what would have started there (slower, exact) and the result carries the warning `RESTORE_REPLAYED`.
- **Faster.** A run that is back on the verified run for 4 ticks stops there (setting "Stop a run that is back on the verified run"; test T24: 30273 -> 3372 simulated ticks, identical windows). The second tick-by-tick scan of the 20 tightest clicks is now off by default ("Tick-by-tick scan of the tightest clicks", 0). The progress popup gives the work about half of each frame (8-40 ms) instead of a fixed 8 ms (a tenth of the time at 14 FPS).
- **Rings.** No growing animation; full strength at once, fully visible for 1 s, then a slow 2 s fade (settings "Ring: seconds fully visible" / "Ring: seconds of fading"). A ring is drawn on the screen where the player was when it clicked and belongs to the replay HUD. Before, it lived in the level and scrolled out of the screen, and a ring that was alive when the replay stopped or the level restarted stayed in the level for good. A release that never mattered shows a grey `any`; a click that could not be measured, a grey `?`.
- The result screen says how many clicks were counted and why not, how exact the recording was, and which clicks were fitted.
- Tests: `tests/run.sh` 489 checks, `tests/verify_sim.sh` 168 checks, `tests/syntax_check.sh` (also covers the new UI code against the stub).

# 0.2.1
Diagnostic build for "Verification failed: The player died at tick 2" (right after Analyze, on any level, noclip or not). **The cause in the real game is not confirmed yet**: nothing here was run in Geometry Dash. This build fixes the parts of the mod that could produce it, and makes the failure say what is going on.
- **The check of the way of stepping now sees deaths.** Before, it only measured how far the player moved in 60 ticks in each way (`processCommands`, or the game's own `update`). A way in which the player moved 2 ticks and then DIED counted as "moved", and when the two distances differed the rule picked `update` - so with `direct +60, update +2` (update kills the player at tick 2) it picked the one that dies, and the verification then died at tick 2 with any macro (auto-repair moved the one click up to 10 ticks in both directions, 20 runs, and could not change a death that happens before the click). Now a way that gets through the 60 ticks alive wins over one that dies; if both die, the one that lasts longer is used; if both are alive, or both die at the same tick, the old rule applies. Reproduced and fixed against the fake game (`tests/verify_sim_test.cpp`, T15-T19).
- **A call of `destroyPlayer` made with the game's own anti-cheat spike is no longer a death.** Noclip mods let that spike through on purpose, which would explain why noclip changed nothing. This needs the member `PlayLayer::m_anticheatSpike` in the SDK; where it does not exist the code compiles without it and does nothing (a [BINDING] guess, see README). The first calls that are ignored are written to the Geode log (`GDFWR: ignored a destroyPlayer call made with the game's anti-cheat spike`).
- **The failure message says what killed the player.** "Killed by: object id 8 at (x, y); player at (x, y)" (or "no object at all"). For a death in the first 60 ticks it also shows how the game was stepped (`stepper: ... direct +60.0 (...), update +2.0 (died at tick 2)`), the player x at the start and at the death, the end portal x, and the started / paused flags. The same lines go to the Geode log: `GDFWR: stepper check`, `GDFWR: stepper probe`, `GDFWR: death at tick`.
- Tests: `sh tests/verify_sim.sh` 131 checks (T15-T21 are new), `sh tests/run.sh` 474 checks, `sh tests/syntax_check.sh` for the glue (also compiled with a stub that does NOT have `m_anticheatSpike`).

# 0.2.0
How the analysis works changed. The aim is NaN GD's way of counting: how much real time one click or one release can move and still survive, in 240 FPS frames.
- **Every action has its own window.** The press window moves only the press (the release stays where it was) and the release window moves only the release. Before, the "input window" moved press and release together (fixed hold), which mixed two things and left Part 9's one-ring-per-action without a clear meaning. The old rule is still there as the setting "Press window moves the release too (old rule)". Clamps follow the new meaning: a press cannot move onto its own release or past the end of the level, a release cannot reach the next press or its own press. Files written by 0.1.x are read as old-rule files and say so ("CLICK" in the result view).
- **Windows are no longer only whole ticks.** The whole-tick count (`early + 1 + late`) stays and is still what the rings show, but every window also stores where the surviving timings really end on each side (`edge` lo/hi) and so its width. With whole-tick runs that is "between n-1 and n+1 ticks": the same macro can read one higher or lower depending on where the click fell inside a tick, exactly like NaN's "6-7 depending on frame alignment". The engine can narrow the width to 1/16 tick by bisection when the simulator can start an input between two physics steps (`ISimulator::supportsSubTick`, `SimInput::sub`). **The real-game simulator cannot do that yet**, so in the game the width is still the 2-tick range; the sub-tick path is tested with a mock only.
- **Long search.** Setting "Search beyond 12 ticks (up to)", default 12 = off. A side that passes all of 1..12 is searched on in steps of 4 and then bisected to one tick, up to the limit (max 120). A window like 30/45 costs about 20 runs per side instead of 75. This assumes pass/fail does not flip back and forth beyond 12 ticks (the pass map and holes/traps still cover only +-12), and the result is marked "long". It saves a second state per click edge during the check, so very long macros reach "Max saved states" sooner.
- **One bucket scheme** for the replay HUD: 1, 2, 3, 4, 5-6, 7-8, 9-12, 13-24, 25+ (nine lines). The replay ring now shows the real count up to 99 instead of stopping at 12. The two new colours are a [DECISION].
- **The precision readout uses the continuous width** (the integer count with whole-tick runs, so the number does not change yet). The model is still the provisional one: it is not confirmed against NaN's calculator.
- **File format:** MACR v2 (every event carries a sub-tick fraction, always 0 for now: reserved for click-between-steps) and ANAL v2 (search limit, rule, edges, widths). Older files still load; a 0.2 file does not load in 0.1.x (that reader drops the analysis section with DERIVED_DROPPED and keeps the macro).
- **Bounded memory instead of "needs more saved states".** A macro with more click edges than "Max saved states (at once)" (default now 1000, was 3000 and a hard stop) is no longer refused. The check keeps no states, and Analyze then measures the clicks in parts: for each part the level is replayed again from tick 0, every tick is compared with the baseline of the check, only that part's states are kept, its clicks are measured, and the states are freed. Short macros take exactly the old way (one replay, no extra time). The parts never split a cluster of close clicks; the share of full scans is split in proportion. The result of the parts is merged and equals the one-pass result (tested on 40 random macros with clusters and on the fake game).
  - Why not a ring buffer of the last 13 states that analyses while the replay goes on: the analysis has to load other states in the middle of the replay and then go back to the replay. If the game restores a state even slightly wrong, the baseline itself would be damaged, silently. Replaying from tick 0 for each part never interrupts the main replay, so the baseline is always the real one, and a replay that does not match the baseline stops with a clear message ("did not match the first one at tick N") instead of giving wrong numbers.
  - Each part starts with the button released and the level restarted; the check against the baseline caught a real problem in the fake-game test (a button still held from the previous part), which is why that release is explicit.
- **Fix: "The TPS changed during the recording" right after pressing Analyze, without touching anything.** The recording marked the TPS as changed when ONE step of level time differed from 1/240 s by more than 0.000001 s. That is far too strict: a time-warp trigger, a lag spike, a pause or a half tick changes the step without any TPS change. Now (1) only whole ticks are compared, (2) a time warp is allowed for (a step equal to 1/240 times the warp, or divided by it, is normal) and the tolerance is 0.2 % instead of an absolute 1e-6 s, (3) the TPS only counts as changed after 12 odd steps IN A ROW, and (4) the warning no longer blocks Analyze: the first step of Analyze replays the macro at 240 TPS, and a macro recorded at another TPS does not survive that replay (the check then says so). A file that says it was recorded at a TPS other than 240 is still refused. When the warning is raised the Geode log now says how long the step was and what the time warp was. Files recorded with the old detector keep the warning but can be analysed now; re-recording is not needed.
- **Build fixes (CI):** Windows: `near` is a macro in `<windows.h>`, so a local variable of that name did not compile in `Session.cpp` (renamed). iOS: the CMake file asked for two architectures (arm64 and x86_64) before the Geode SDK set one for iOS, which gave "CMAKE_APPLE_ARCH_SYSROOTS is not the same length as CMAKE_OSX_ARCHITECTURES"; iOS now uses arm64 only (macOS keeps both).
- **Pause screen:** the GDFWR button is now a round green button ("FW") on the LEFT side of the pause screen (in the game's own left button menu when there is one, otherwise in a menu of its own at the left edge). It was a long rectangular button on the right.
- **All platforms.** The CI now also builds macOS and iOS next to Windows and Android 32/64 (the mod.json already declared them). The code adds nothing platform-specific: no file, thread or OS API, only the standard library and what the mod already used; the core compiles warning-free with `-Wall -Wextra -Wpedantic -Wshadow -Wconversion`. It was NOT built with the Apple or Android toolchains here.
- **Not done in this version** (said plainly): sub-tick input in the real game (`GameSimulator` cannot start an input between two physics steps; the engine and the file are ready for it). The state is compared exactly (hash and per-tick samples, no epsilon); the old epsilon field stays in the file format, always 0.
- Tests: `sh tests/run.sh` 474 checks (also under ASan/UBSan), `sh tests/verify_sim.sh` 104 checks (the fake game now saves and restores real states), `sh tests/syntax_check.sh` for the glue.

# 0.1.3
- **Auto-repair of a failed verification.** When the player DIES during the check, the click that is to blame is moved and the run is tried again: first `+1, +2 ... +10` ticks (later), then `-1, -2 ... -10` ticks (earlier). The click holding at the moment of death goes first; the next click (it may have been too late) goes second. The whole click moves together, so the hold time stays the same. The first shift that reaches the end of the level is kept: the file becomes EDITED, a message lists what moved, and Edit clicks > Restore all brings the original back. If nothing helps, the file is left exactly as it was and the original failure is reported. Up to 5 trouble spots are repaired one after the other. Settings: "Auto-repair a failed verification" (on) and "Auto-repair: largest shift" (10).
- **Replay now only needs a macro.** It is enabled whenever the file has a macro, even before any analysis or verification, so you can watch whether the macro passes. Without a CURRENT analysis the rings are grey and nothing is counted; a message says why. Replay is off (grey, tap says why) when there is no macro. When the player dies in a replay, the message names the tick.
- Fix attempt for "The run did not reach the end of the level" on a normal level (still happening in 0.1.2):
  - The silent replay now CHECKS that the player moves before it starts: the level is run for 60 ticks in each way of stepping the game (`processCommands`, or the game's own `update`), with and without the game's delayed start (`startGame`), and the way that moves the player is used. If the player moves in none of them, the failure says so at once instead of after two minutes of nothing.
  - The pause menu is closed while Analyze runs (a paused game does not run) and comes back afterwards.
  - The end portal is also looked for among the level objects if the game's own pointer is empty; a RECORDED run that is still alive at the tick where the live run ended counts as finished when no end portal can be found at all.
  - The failure message now shows the facts that matter: the way of stepping, player x at the start and now, end portal x, level time, started / paused / end-animation flags and the mod version.
  - If the macro plays without dying but the end is not detected, Analyze offers to measure the clicks anyway (the file stays NOT_VERIFIED).
- The panel title shows the mod version.
- Tests: `sh tests/verify_sim.sh` runs the real verification / repair state machine against a fake game (54 checks); `sh tests/run.sh` has 346 checks.

# 0.1.2
- Fix: verification always failed with "The run did not reach the end of the level", even for a level with one spike and one jump. The game calls `levelComplete()` only some real time after the end animation starts, and the silent re-simulation is far faster than real time, so that call never came. The end of the level is now detected from the tick-driven facts (the `playEndAnimationToPos` hook, the game's end-animation flag, the player reaching the end portal). A level with a long run after the last click is no longer cut off after 30 s, and a failure report shows the player and portal positions.
- The **Verify** button is gone. **Analyze** runs the whole process: check the macro (step 1 of 2), then measure the clicks (step 2 of 2). An imported file can be analysed directly; the "Import finished" prompt now offers Analyze.
- The level time stored after a verification (`endTick`) is now the tick where the end of the level is reached, not the tick where the end animation finished.
